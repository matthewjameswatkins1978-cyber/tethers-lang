## Requested outcome

Introduce the `together` fan-out / join block as deterministic language
semantics in the OCaml engine: a Tether may declare several independent Actions
as one concurrency group with a join before later Actions, without turning the
language into a scheduler and without requiring physical parallel execution.
The C1 reference runtime may execute group members serially in deterministic
source order as one valid schedule. P6 closeout wording must show P6 FINAL
ACCEPTED at `5ed7634d8abc4056e0faa1ff09924377dec6e645`, with nothing beyond C1
started.

## Decisions and assumptions

- Plan representation is additive: `plan.actions` stays the flat, ordered
  source-order serial schedule (a valid C1 schedule); `plan.groups` declares
  each group's `group_id` (`group_1`, `group_2`, …) and `member_action_ids` by
  reference, present only when at least one `together` block exists.
- Action IDs remain globally position-derived across the whole plan; group
  members receive contiguous IDs; `idempotency_key` stays
  `evaluation_id/action_id`.
- One `group_planned` Trail entry follows each group's last `action_planned`
  entry (the planning-level join point); sequences stay contiguous and
  causal.
- `tethers.validate` `action_count` semantics: total planned Actions, members
  flattened. Existing validate transcripts are unchanged because pre-C1
  sources contain no `together` blocks.
- `together` is reserved as a keyword at the `do` level; names such as
  `together.foo` remain ordinary Action names.
- Language/protocol versions stay `0.1`; this packet is the explicit design
  gate that adds `together` to the 0.1 language, recorded in SPEC.md.
- The OCaml switch used is the pre-existing verified directory switch
  `D:\The Next Thing\Tethers Lang\tethers-0.1\engine-ocaml` (OCaml 5.5.0,
  Dune 3.24.0, Yojson 2.2.2, matching the locked baseline); the packet names it
  as `OCaml switch path`. Test scripts that do not accept a switch argument
  were run with `OPAMSWITCH` set to that exact switch.

## Discoveries

- `test-mcp-transcripts.ps1` uses a hard-coded required-case list, not
  auto-discovery; a new transcript case must be registered there.
- The engine's JSON-lines protocol expects exactly one compact JSON object per
  line; multi-line pretty-printed requests are read as separate lines
  (`invalid_json` per line), so fixtures and drivers must send compressed JSON.
- `plan_items` preserves the pre-existing error contract exactly: a member
  planning failure produces the correlated envelope with one
  `action_planning_failed` entry at `next_sequence` and without partial
  `action_planned` entries, identical to ordinary multi-Action planning.
