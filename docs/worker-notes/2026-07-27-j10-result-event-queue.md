## Requested outcome

After one evaluation finishes and creates a standard Result Anchor, place that
Anchor at the end of a host-owned FIFO queue. The host then evaluates queued
Result Anchors one at a time in FIFO order, without recursion, parallelism, or
retry. A Result Anchor generated by a queued evaluation is appended to the tail.

## Decisions and assumptions

### Queue design

- `ResultEventQueue` wraps `VecDeque<ResultAnchor>` internally; the
  `VecDeque` is not exposed to callers.
- Queue is non-persistent in-memory; persistence is deferred.
- FIFO order is guaranteed by `push_back` / `pop_front`.

### Causal context

- `InputEventContext` carries `event_id`, `correlation_id`, `generation`.
- Initial external event: correlation = event_id, generation = 0.
- Generated Result Anchor: correlation = root event ID, causation = parent
  anchor event ID, generation = parent generation + 1.
- Generation uses `u32::checked_add(1)`; overflow returns `None` and fails
  closed (no anchor built, written, or enqueued).

### Queueing writer ordering

- `QueueingResultAnchorWriter::write` first calls
  `ResponseResultAnchorWriter::write` (which sets `response["result_anchor"]`)
  and only on `Ok(())` enqueues the typed anchor.
- A failed write returns `Err(())` before the enqueue branch; the typed
  anchor is never appended to the queue.

### Follow-up request construction

- `build_follow_up_request` deep-clones a pristine copy of the original
  request captured once in `main()` before any mutation.
- Replaces event with the Result Anchor's `event_id`, `event_name`, and
  serialized Facts object (direct, not wrapped).
- Replaces top-level external `facts` with `{}`.
- Preserves `protocol_version`, `language_version`, tether source, and
  capabilities unchanged.

### Follow-up evaluation ID

- `eval_followup_<lowercase SHA-256 hex of UTF-8 event_id>`.
- Deterministic, fixed length, no raw payload included.

### Coordinator structure

- `process_one_event` processes one event completely and may enqueue via
  `QueueingResultAnchorWriter`.
- Outer loop in `main()` drains the queue with `while let Some(anchor) =
  queue.pop_front()`.
- No recursive call to `process_one_event`, no `queue.pop_front` inside
  `process_one_event`.
- No thread, async runtime, retry loop, or parallel worker.

### J09 replay preservation

- Follow-up evaluations derive new `(original_event_id, evaluation_id,
  action_id)` triples via `LogicalExecutionKey::derive`.
- The original admission triple is never touched.
- Recovered replay state and provider-call counts remain exactly as J09
  established.

### Part 3 inspection findings

1. `main` only drains the queue: the drain loop is the explicit `while let
   Some(anchor) = queue.pop_front()` block at the end of `main()`.
   `process_one_event` is the only function that enqueues via
   `QueueingResultAnchorWriter`.
2. `process_one_event` never drains the queue: no `queue.pop_front` call
   inside the function body. The recursion guard test
   (`j10_process_one_event_does_not_recursively_invoke_itself`) searches for
   any `process_one_event(` call and for any `queue.pop_front` reference and
   asserts both are absent.
3. Pristine request template is captured once in `main()` via `let
   pristine_template = request.clone();` before any mutation.
   `j10_follow_up_request_leaves_pristine_template_unchanged` proves the
   template is never mutated.
4. Every generated Anchor's `generation` is `input_context.next_generation()`
   which returns `self.generation.checked_add(1)`.
   `j10_generation_overflow_enqueues_nothing` proves `u32::MAX` generation
   returns `None` and no Anchor is built, written, or enqueued.
5. Only a successfully written standard Result Anchor enters the queue.
   `QueueingResultAnchorWriter::write` first calls the inner writer and only
   on `Ok(())` enqueues. A failed write returns `Err(())` immediately.
6. J09 replay admission is keyed on the exact `(original_event_id,
   evaluation_id, action_id)` triple. Follow-up evaluations use new triples.
   The original admission is never touched.
7. No thread, async runtime, retry loop, or parallel worker exists. The only
   `thread::spawn`-style symbol is a test guard. `process::Command::new`
   appears once inside `call_engine` for the engine invocation.

## Discoveries

### Part 3B stray REPLACE token

The previous Part 3 commit (`69decee`) contained a stray `REPLACE` token at
the end of `j10_production_no_env_var_bypass` that would break compilation.
This was discovered during the test correction pass and removed.

### Constructor-only chain test was insufficient

The original A→B chain test (`69decee`) manually constructed A and B anchors
without driving the real coordinator seam. It was replaced with a seam-driven
test flowing through `authorise_and_execute_inner`, `TestReplayAuthority`,
and `QueueingResultAnchorWriter`, which exercises the real queue, replay
admission, and dispatch paths end to end.

### Production with-follow-up binary route blocked by design

The production binary cannot demonstrate the with-follow-up path through the
public CLI because the demo capability's structured scope has no
scope-assessment input surface. This is an intentional later-configuration
boundary, not a J10 defect. No bypass mechanism was added.

### Native Windows replay not rerun during J10

The native Windows replay tests (`native_recovered_runtime_test!`s) were not
executed in the non-Windows development environment. The test code is present
and unchanged from J09.

## Remaining risks

- Production with-follow-up binary route awaits a later public
  structured-scope configuration boundary. Until that boundary exists, the
  with-follow-up coordinator path can only be exercised through the internal
  test seam.
- Native Windows replay was not rerun during J10. The replay behaviour is
  covered by cross-platform replay tests and the Windows-specific test code
  is unchanged from J09.
- J11 duplicate-ID rejection and depth-eight enforcement remain out of scope.
  A queue that is fed duplicate event IDs or exceeds eight generations will
  not be rejected until J11 is implemented.
