## Decisions and assumptions

- Path hardening follows the same pattern as `m3_store::StoreRoot::open()`: `verify_chain` before canonicalisation, `fs::canonicalize`, then `verify_chain` + `reject_reparse` after.
- `canonicalize_scope_value` walks schema and scope in parallel. It processes `properties`, `items`, and schema-valued `additionalProperties`. Scalars and unannotated nodes pass through unchanged.
- UTF-8 conversion via `Path::to_str()` fails closed if the canonical path is not representable as valid UTF-8 (unlikely on Windows with typical directory names).
- The first validation pass catches type errors (e.g., non-string on a string-typed property) before canonicalisation attempts a filesystem call.
- Existing `validate_operational_scope` kept for backward compatibility (used by R1B tests).

## Discoveries

- The `canonicalize_directory_path` function naturally integrates with the existing `m3_store` path hardening primitives without modification.
- `verify_chain` iterates all ancestors up to root, handling `NotFound` gracefully for non-existent intermediate components. This means a junction ANYWHERE in the path chain (including above the target directory) triggers refusal.
- The triple validation flow (validate → canonicalise → re-validate) ensures that canonicalised paths still conform to the original schema constraints (type, enum, pattern, etc.).
