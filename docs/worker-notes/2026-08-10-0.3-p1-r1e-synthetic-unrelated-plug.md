## Discoveries

- The R1E positive enablement shortcut (`OperationalScopeEvidence::create` + `EnablementStore::enable`) was architecturally sound but did not prove the generic pipeline end-to-end. The fix routes all positive tests through the same CLI path the negative tests already used.
- The `plug enable` CLI internally constructs `OperationalScopeEvidence` from the validated/canonicalized scope, then calls `EnablementStore::enable`. Loading the record afterward proves the full chain succeeded.
- The determinism proof required two separate installations because a single plugin can only be enabled once (state transitions from `present_disabled` to enabled). Comparing `canonical_scope_json` + `scope_schema_digest` across installations proves deterministic behaviour without falsely claiming all fields are invariant.
- The `m3_fixture_provider` binary is the only test binary that can serve as a synthetic provider payload for conformance. Its identity (`tethers-stdio-fixture`) and tool name (`fixture_ping`) are hard-coded and must match the package manifest.
- Without a real executable provider binary, the conformance layer (`run_host_conformance`) fails at `CreateProcessW`. This is a genuine architectural constraint: package installation requires a real provider executable for conformance.
- `fs::canonicalize()` on Windows returns `\\?\`-prefixed paths when the input is a `PathBuf` from `std::env::temp_dir()`, but returns non-prefixed paths when given a plain string path. Tests normalize both sides for comparison.
- The generic machinery continues to handle new Plug identity + scope shape without any production-side knowledge, as expected.
