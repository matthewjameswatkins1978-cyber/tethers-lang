## Generation 0 — Intent Recorded

Generation 0 establishes the replay intent.  It is published immediately
after the planner proposes an Action.  precedence claim_digest (above)
serves as the predecessor.

state_data: {"intent_recorded":true}

## Ledger Chain Validation

  Gen 0 claim (identity) -> Gen 0 (intent_recorded)
  Gen 0 predecessor = identity_claim.claim_digest  ✓
  Gen 1 predecessor = gen 0 record_digest           ✓
  Gen 2 predecessor = gen 1 record_digest           ✓
  Gen 2 is terminal (Succeeded)                     ✓

## Key Properties

- The logical_key_digest is the same for all generations (same planner tuple).
- The execution_id_digest is the same for all generations (same dispatch).
- Each generation's predecessor_digest links to the previous generation.
- Tampering with any field breaks the chain (digest mismatch fails closed).
- Replay recognises the identity claim, walks generations 0..2, and returns
  the terminal durable_outcome_digest.

## Immutable Atomic Record Property

Replay generation files are written as immutable atomic records via
write-then-rename on Windows (NTFS).  Once a generation file is written,
it is never modified.  Generation 1 transitions from gen 0; a corrupt or
missing gen 0 fails the entire ledger closed.
