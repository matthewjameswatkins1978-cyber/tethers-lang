## Objective

After one evaluation finishes and creates a standard Result Anchor, place that
Anchor at the end of a host-owned FIFO queue. The host must then evaluate queued
Result Anchors one at a time, in stable first-in-first-out order, only after the
current evaluation has completely returned, without recursive stack execution,
without parallel evaluation, and without retrying a failed queue item.

A Result Anchor generated by a queued evaluation is appended to the tail. It
must not jump ahead of events already waiting.

## Relevant background and existing behaviour

J09 introduced durable replay: every admitted provider invocation records a
replay outcome bound to a deterministic `(original_event_id, evaluation_id,
action_id)` triple, stored on durable storage and used for exact recovery of
past decisions without re-executing provider calls.

Before J10, the host processed exactly one external event per invocation. When
that event produced a Result Anchor, the anchor was written into the response
but never fed back into the coordinator. There was no mechanism for chained or
follow-up evaluation.

The accepted J09 base commit is
`8ee9b19d01efb02b2c6a8483ff2c5e97cbbb9d86`. All J10 implementation is atop
that commit through the dedicated branch `cline/j10-result-event-queue`.

## Required behaviour

1. Host-owned FIFO Result Anchor queue: the host maintains a
   `ResultEventQueue` wrapping an opaque `VecDeque<ResultAnchor>` with
   narrow operations `enqueue`, `pop_front`, `is_empty`, and `len`.

2. Initial evaluation completes before queue drain: `process_one_event`
   handles the initial external event completely and returns before any
   queued anchor is processed.

3. One queued event processed at a time: the outer coordinator loop drains
   the queue by popping the oldest anchor and processing it fully through
   `process_one_event` before popping the next.

4. Child Result Anchors append behind existing siblings: when a queued
   evaluation generates a new Result Anchor, it is appended to the tail
   of the queue and does not jump ahead of events already waiting.

5. No recursion, parallelism, retry or reinsertion: `process_one_event`
   never calls itself and never calls `queue.pop_front`. The binary is
   a single-process single-thread executor with no async runtime, no
   thread pool, and no retry loop for failed queue items.

6. Pristine-template follow-up request mapping:
   `build_follow_up_request` deep-clones a pristine copy of the original
   request captured before any mutation, replaces the event fields with
   the queued anchor's event identity and serialized Facts, replaces the
   top-level external facts with `{}`, and preserves protocol_version,
   language_version, tether source, and capabilities unchanged.

7. Deterministic follow-up evaluation ID: follow-up evaluations use
   `eval_followup_<lowercase SHA-256 hex of UTF-8 event_id>` as a
   deterministic, fixed-length identifier with no raw payload inclusion.

8. Correlation, causation and checked generation: every generated Result
   Anchor carries a `correlation_id` (root event), `causation_id` (parent
   anchor event ID), and `generation` (parent generation + 1 via
   `checked_add`). Generation overflow fails closed and enqueues nothing.

9. J09 replay and provider-call preservation: follow-up evaluations
   derive new `(original_event_id, evaluation_id, action_id)` triples
   for replay admission without touching the original admission.
   Recovered replay state and provider-call counts remain exactly as
   J09 established.

10. Fail-closed enqueue-zero branches: every branch that produces zero
    provider calls (unmatched, Ask, Deny, Unavailable, missing replay
    root, Trail intent failure, pre-provider deadline expiry, g1/g2
    publication failure, durable outcome failure, writer failure,
    generation overflow) enqueues nothing.

11. Conditional `follow_up_evaluations` reporting: the initial response
    includes a `follow_up_evaluations` array when at least one queued
    event was evaluated, and omits it otherwise.

12. Public production scope limitation remains unchanged: the production
    binary has no public mechanism to establish structured permission
    scope for follow-up evaluation; this is deferred to a later
    runnable-configuration boundary. No bypass, flag, or configuration
    mechanism was added.

## Frozen decisions and invariants

- Queue is host-owned, FIFO, non-persistent in-memory `VecDeque`.
- Queue drain is an explicit outer `while let Some(anchor) = queue.pop_front()` loop.
- `process_one_event` must never drain the queue, call itself, or spawn a thread.
- Pristine request template is captured once before any mutation.
- Follow-up evaluation ID is `eval_followup_<SHA-256 hex of UTF-8 event_id>`.
- Generation uses `u32::checked_add(1)` with fail-closed overflow.
- `QueueingResultAnchorWriter` writes the response anchor first, then enqueues;
  a failed write prevents the enqueue.
- No duplicate event-ID rejection or depth-eight enforcement (these are J11).
- No queue persistence, no parallel evaluation, no retry.
- OCaml engine, protocol, and planner are unchanged.

## Acceptance criteria

1. The `ResultEventQueue` exposes only `enqueue`, `pop_front`, `is_empty`,
   and `len` with no internal `VecDeque` exposure (`tests::j10_queue_*`).

2. `process_one_event` handles the initial external event and returns before
   the outer drain loop begins
   (`tests::j10_initial_event_completes_before_queue_drain`).

3. The outer loop drains one anchor at a time, popping only after
   `process_one_event` returns for the previous anchor
   (`tests::j10_queue_drain_is_serial`).

4. A child anchor generated during a queued evaluation is appended behind
   any existing siblings and never processed out of order
   (`tests::j10_child_appends_behind_siblings`).

5. `process_one_event` contains no recursive call to itself and no
   `queue.pop_front` call inside its body
   (`tests::j10_process_one_event_does_not_recursively_invoke_itself`).
   No `thread::spawn` or async runtime exists in production code.

6. `build_follow_up_request` deep-clones the pristine template, replaces
   event fields with anchor identity and serialized Facts, clears external
   facts to `{}`, and preserves protocol_version, language_version, tether
   source, and capabilities (`tests::j10_follow_up_request_*`).
   `j10_follow_up_request_leaves_pristine_template_unchanged` proves the
   template is never mutated.

7. Follow-up evaluation IDs are deterministic `eval_followup_<SHA-256 hex>`
   with no payload inclusion (`tests::j10_follow_up_evaluation_id_*`).

8. Every generated anchor carries correct `correlation_id` (root),
   `causation_id` (parent anchor event ID), and `generation` (parent + 1)
   (`tests::j10_correlation_causation_*`,
   `tests::j10_initial_to_a_to_b_chain`).

9. J09 replay admission triples are preserved for follow-up evaluations;
   recovered replay state and provider-call counts are unchanged
   (`tests::j09_runtime_*`, `native_recovered_runtime_test!`s).

10. All enqueue-zero branches (unmatched, Ask, Deny, Unavailable, missing
    replay root, Trail intent failure, pre-provider deadline expiry, g1/g2
    publication failure, durable outcome failure, writer failure, generation
    overflow) produce zero queue additions and zero provider calls
    (`tests::no_result_anchor_on_*`, `tests::j09_runtime_*`,
    `tests::j06_deadline_before_invocation_is_unattempted_without_provider_outcome_or_anchor`,
    `tests::j10_generation_overflow_enqueues_nothing`).

11. `follow_up_evaluations` is present in the response only when at least
    one queued event was evaluated, and absent otherwise
    (`tests::j10_follow_up_evaluations_*`,
    `tethers-0.1/scripts/test-host-result-follow-up.ps1` smoke Phase 2).

12. No environment variable, flag, or configuration mechanism bypasses the
    production scope limitation; `j10_production_no_env_var_bypass` confirms
    `TETHERS_J10_SMOKE_SCOPE` is absent from all source files and no
    replacement exists.

## Stop conditions

- A test that already passed on J09 regresses.
- `process_one_event` calls itself or drains the queue.
- A queued anchor is processed out of FIFO order.
- A child anchor jumps ahead of existing siblings.
- Generation arithmetic overflows without failing closed.
- Any enqueue-zero branch enqueues an anchor.
- A follow-up request mutates the pristine template.
- The production binary exposes a scope-bypass mechanism.
